Build 1 — Create the email triage Routine

Model: Sonnet (Claude Sonnet 4.6) · Time: 25 min

Set up Gmail and GitHub connections, then create a Remote Routine running a categorizer-only stub on a daily schedule.

Steps:

In the desktop app sidebar: Customize → Connectors → connect Gmail via OAuth (connectors set up here work in both interactive sessions and Routines).

Set up GitHub (Remote Routines clone a repo at the start of each run):

New account: github.com/signup → email, password (15+ chars, or 8+ with number+lowercase), username, solve human-check, verify email, pick Free plan, skip personalization.

New repo: github.com/new → name email-manager (lowercase, dash), Private visibility, leave README/.gitignore/license unchecked → Create repository (ignore the git-commands page shown after).

Connect GitHub to Claude Code: at claude.ai/code, click the Connect/Set up GitHub banner, sign in, choose "Only select repositories" → select email-manager → Install & Authorize.

In the desktop app sidebar: Routines → New routine → Remote.

Name: Email Triage. Paste the categorizer-stub prompt, model = Claude Sonnet 4.6.

Under Repositories, add the email-manager repo.

Leave Environment as Default (Trusted network access).

Under trigger: Schedule → Daily → 8:00 AM local time (auto-converted to UTC).

In the Connectors tab, ensure only Gmail is checked (remove anything not needed for a tightly scoped routine).

Click Create, then open the routine and click Run now — watch it call the Gmail connector, classify emails, and print a tally.

Confirm output looks reasonable (perfect accuracy isn't the goal yet — that's Build 3). Leave the schedule as-is; Build 2 upgrades the prompt before it's relied on.

Reusable prompt — categorizer stub:

You are an email triage assistant running as a scheduled routine. You operate without user supervision and produce output to the run log.

Steps:

1. Use the Gmail connector to fetch up to 20 unread emails matching `is:unread newer_than:1d`. For each message, capture: ThreadId, Subject, Sender, and a body snippet of roughly 500 characters.

2. For each email, output a single classification line followed by a one-sentence reason:

NEEDS_REPLY

Reason: <one sentence>

or

NO_REPLY

Reason: <one sentence>

NEEDS_REPLY when:

- Someone asked a direct question

- You're being waited on for something

- Action is required from you

NO_REPLY when:

- Newsletters, notifications, or automated messages

- FYIs that don't need a response

- Emails where someone else is handling it

3. After processing all emails, print a final tally: total processed, count of NEEDS_REPLY, count of NO_REPLY.

Do not ask for clarification. If Gmail returns zero emails, say so and exit cleanly.



Go further: pin the routine to a private repo with your own prompt files.

Build 2 — Upgrade the Routine with reply drafting + Slack

Model: Sonnet · Time: 20 min

Expand to a full email manager: 4-way classification, drafted replies saved to Gmail, and a Slack DM summary.

Steps:

Customize → Connectors → connect Slack via OAuth to the target workspace.

Routines → Email Triage → Edit routine (pencil icon).

Replace the entire Prompt field with the full email-manager prompt below.

Under Connectors, confirm both Gmail and Slack are checked; remove anything else.

Save changes, then Run now.

Verify in Gmail Drafts that new drafts appeared on urgent/non-urgent-needs-reply threads, and check Slack for the summary DM.

Routine stays on its Build-1 daily 8 AM schedule — check the "Repeats" section on the routine's detail page for next run time.

Reusable prompt — full email manager:

You are an email manager running as a scheduled routine. You operate end to end without user supervision and produce output to the run log.

Steps:

1. Use the Gmail connector to fetch up to 20 unread emails matching `is:unread newer_than:1d`. For each message, capture: ThreadId, Subject, Sender, IncomingEmail (body snippet roughly 500 chars).

2. For each email, classify into exactly one of these four categories:

- `urgent` - direct question or action required from you in the next 24h

- `non-urgent-needs-reply` - direct question or action required, no urgency

- `fyi` - informational, no reply expected, but worth knowing

- `noise` - newsletters, notifications, automated messages, irrelevant

Output a single JSON object per email with fields: ThreadId, Subject, Sender, IncomingEmail, AICategorization.

3. For every email categorized as `urgent` or `non-urgent-needs-reply`, draft a reply. Write in the voice of someone direct, warm, and brief. Match the length of the incoming email. No em dashes. No filler. Open with "Hi <first name>," and only the body, no subject line. Use the Gmail connector to save each draft to Gmail Drafts on the same ThreadId.

4. After all emails are processed, use the Slack connector to post a single DM to my Slack with this format:

Daily email triage - <date>

Processed: <total>

Drafts saved: <count of urgent + non-urgent-needs-reply>

Top 3 urgent:

- <Subject> from <Sender>

- <Subject> from <Sender>

- <Subject> from <Sender>

If there are zero urgent items, skip the "Top 3 urgent" block.

Do not ask for clarification. If Gmail returns zero emails, post a one-line Slack summary that says so and exit cleanly.



Go further: send yourself a text instead of Slack.

Build 3 — Classification eval logged to your repo

Model: Haiku · Time: 20 min

Measure classification accuracy against human-labeled ground truth, tracked as a version-controlled markdown file.

Steps:

Enable direct pushes to main: Routines → Email Triage → Edit routine → Permissions tab → toggle on "Allow unrestricted branch pushes" for the email-manager repo (otherwise routines write to a claude/-prefixed branch requiring manual merge).

Insert the eval-logging step (below) as Step 3.1, just before the existing Slack-summary Step 4.

Replace Step 4 with the upgraded version that adds eval-file links to the Slack message.

Save changes, Run now.

In Slack, open the evals/eval-1.md link on GitHub — a table with one row per email, TODO in the HumanCategorization column.

Label ground truth directly on GitHub.com: click the pencil ("Edit this file"), replace each TODO with urgent / non-urgent-needs-reply / fyi / noise (exact lowercase spelling), leave AICategorization untouched, then "Commit changes" (confirm the dialog).

Run now again — Claude reads the labels, computes accuracy, updates the header line, and posts the new accuracy in Slack. Target 90%+.

If accuracy is short of target, use either lever (re-editing the routine and re-running each time):

Prompt updates: share the eval file + current routine prompt with a regular Claude Code session and ask it to diagnose disagreements and propose fixes.

Determinism: add "Be deterministic. Apply the category definitions strictly. If a borderline email matches two categories, pick the higher-severity one (urgent > non-urgent-needs-reply > fyi > noise)."

Reusable prompt — Step 3.1 eval logging:

3.1. Write the eval log to the repo.

First, read the cloned repo's git remote URL to figure out the GitHub username. Store it as <github_user>.

If the file `evals/eval-1.md` does not exist, create it with this header:

# Eval #1: Email Triage Classification

Accuracy: (pending labels)

| ThreadId | Subject | Sender | IncomingEmail | AICategorization | HumanCategorization | Accuracy |

| --- | --- | --- | --- | --- | --- | --- |

For each email from Step 2, either append a new row to the table or update the existing row (match on ThreadId). Each row should contain:

- ThreadId

- Subject

- Sender (just the name or email)

- IncomingEmail (truncate to 200 chars to keep the table readable, escape pipe characters as \|)

- AICategorization (the label from Step 2)

- HumanCategorization (if the row already exists with a human label, preserve it; otherwise write TODO)

- Accuracy (if HumanCategorization is filled in: "Accurate" if it matches AICategorization, "Inaccurate" otherwise; if HumanCategorization is TODO, leave Accuracy blank)

After updating the table, count how many rows have HumanCategorization filled in (not TODO) and how many of those match AICategorization. Update the "Accuracy:" line at the top with: "<accurate count> / <labeled count> = <percentage>%". If no rows have labels yet, leave as "(pending labels)".

Commit the file to main with the message: "Eval #1 update - <today's date>"

Build 4 — LLM-as-a-judge eval

Model: Sonnet (Opus 4.8 as an optional escalation) · Time: 20 min

Add a self-scoring pass that grades every drafted reply against a 4-criterion rubric — no manual labeling required.

Steps:

Insert Step 3.2 (self-judge, below) right after Step 3.1 and before Step 4.

Replace Step 4 with the final version adding the judge-file link.

Save changes, Run now.

In Slack, click the ⚖️ link to see per-draft scores, rationale, and the running average.

Review the rubric (Tone, Length, Context, Actionability — each 1–4) and adjust based on what's seen.

If the average isn't where you want it, use any of three levers:

Prompt updates: share the judge file + routine prompt and get back a full updated prompt with fixes to the drafting instructions.

Determinism: add "Be deterministic. Apply the anchors strictly. Use the same score for two drafts of equivalent quality" to the rubric section.

Model: switch the routine's model to Claude Opus 4.8 if prompt updates aren't moving the needle.

Iterate by re-running on the same 24-hour window and checking the average score line — target 14+ out of 16 on the test set.

Reusable prompt — Step 3.2 self-judge:

3.2. Self-score each draft you just generated against the rubric below. Be strict and consistent.

Rubric (each criterion 1-4):

Tone: does it sound like a real person, no AI tells?

1: Robotic, stiff, or overly formal. Uses hedging or AI-style filler.

2: Mostly readable but noticeable AI-isms. Em dashes, over-explanation, or unnatural phrasing.

3: Sounds like a real person. Contractions used. Minor awkward phrasing.

4: Indistinguishable from how a human would write it.

Length: does the draft match the weight of the incoming email?

1: Grossly mismatched.

2: Noticeably too long or too short.

3: Roughly appropriate.

4: Perfectly calibrated.

Context: does the draft engage with what was actually asked?

1: Ignores or contradicts the email.

2: Generic, misses key specifics.

3: Correctly engages, minor details missed.

4: References specifics, no hallucination.

Actionability: does the draft move the conversation forward?

1: Vague, non-committal.

2: Partially moves things forward.

3: Answers the question or closes the loop.

4: Advances decisively. Send-ready.

Write the scores to `evals/judge.md` in the repo. If the file does not exist, create it with this header:

# Eval #2: Reply Draft Quality (LLM-as-Judge)

Average score: (pending)

---

For each scored draft, either append a new section or replace the existing section for that ThreadId. Each section looks like:

## <Subject> (ThreadId: <ThreadId>)

**From:** <Sender>

**Incoming:** <one-sentence summary of the incoming email>

**Draft:**

> <the actual draft text, blockquoted>

**Scores (total: <sum>/16):**

- Tone: <1-4> - <one-sentence rationale>

- Length: <1-4> - <one-sentence rationale>

- Context: <1-4> - <one-sentence rationale>

- Actionability: <1-4> - <one-sentence rationale>

---

After writing all sections, calculate the average total across all drafts in the file and update the "Average score:" line at the top with: "<average> / 16".

Commit the file to main with the message: "Eval #2 update - <today's date>"
