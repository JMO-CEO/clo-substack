Build 1 — Document a process you want to build subagents for

Model: Sonnet · Time: 20 min

Manually map a real work process to a subagent architecture before writing any code. Recommended to pick a process from one of two patterns:

Outreach processes — cold sales outreach, candidate sourcing, partnership development, job search

Knowledge synthesis processes — support ticket triage, email triage, customer insights, bug reporting, feature request synthesis

Steps:

List out each step of the chosen process manually, as high-level instructions for a person to follow.

In a new session in the Chief of Staff agent folder, give AI the step list and have it propose 2–3 subagents and their roles.

Collaborate until settled on 2–3 subagents with short descriptions each. Every documented step should map to a subagent, though one subagent can own more than one step.

Reusable prompt — propose subagents for a process:

Suggest 2-3 subagents and their roles for creating an [your task] system led by my chief of staff agent.

Context:

The task process is:

1. [Step 1]

2. [Step 2]

3. [Step 3]



Go further: research existing agent systems; map a second process.

Build 2 — Diagram your agent system

Model: Sonnet · Time: 15 min

Turn the subagent plan into a shared visual diagram the agent can read and you can update like code — labeling inputs, outputs, and roles for each subagent.

Steps:

In the same session as Build 1, run the diagramming prompt to generate an HTML5 diagram of the Chief of Staff (orchestrator) plus subagents, saved to diagrams/agent-system-diagram.html.

Preview it (ask Claude to render it, or open in a file explorer/browser).

Refine using the reference examples (Cold Outreach Agent System / Cold Outreach Agent Flow) as inspiration or context.

Reusable prompt — build the system diagram:

Goal: Using HTML5, diagram my agent system. My chief-of-staff agent acting as orchestrator, plus the subagents identified above. Keep it visual, not text-heavy: each agent gets a short role tag, one plain-spoken sentence on what it does, and two inputs/two outputs max, no bullet-heavy paragraphs. Include the approval gate and a one-line flow summary at the bottom.

Context: write it like a person explaining it to a colleague, not a spec doc. No em dashes or en dashes anywhere, in copy or in code comments, use commas or periods instead. Match the [your design skill]-design skill for visual polish, but let the copy stay plain and conversational rather than clinical.

Rules:

Save the diagram to diagrams/agent-system-diagram.html



Go further: build with a dedicated diagramming tool; mark a trust level on each subagent.

Build 3 — Build your first subagent

Model: Sonnet · Time: 20 min

Create the first subagent .md file (living in .claude/agents/) and wire a routing rule in CLAUDE.md so the orchestrator knows when to hand off to it.

Steps:

Pick one subagent from the diagram; in a new session from the Chief of Staff folder, run the subagent-identity prompt — it pulls name/role/inputs/outputs from the diagram and asks up to 3 clarifying questions (edge cases, unsupervised vs. escalation boundaries, what good output looks like), using the permission model already set in the Chief of Staff identity file.

Add a routing rule to CLAUDE.md pointing to the new subagent's file via the routing prompt.

Test by asking the orchestrator to complete a task that clearly should delegate to the new subagent.

Reusable prompt — build the subagent identity file:

Goal: Write a subagent file for [subagent name], with a name, description, and system prompt. Pull the name, role, inputs, and outputs directly from the diagram above, don't ask me to restate them.

Context: I want to brainstorm conversationally with you to decide the things the diagram doesn't cover: edge cases when input is missing or malformed, what this agent can do unsupervised versus when it escalates, and what good output looks like for it specifically. Use the permission model already established in the chief-of-staff identity file from this conversation to answer the escalation question, and reference the chief-of-staff agent by the name already set there. Ask no more than 3 questions, then write the system prompt from our brainstorm plus the diagram.



Reusable prompt — add the routing rule:

Goal:

Create a routing rule for you as the orchestrator agent of when to use the subagent [subagent name]

Context:

I want this routing rule to live in the CLAUDE.md and have it point to the [subagent name].md file in the .claude/agents folder

Rules:

- Keep the routing rule short in CLAUDE.md so it mostly points to the .claude/agents folder files



Go further: give it a memory; run it on a cheaper model.

Build 4 — Build additional subagents

Model: Sonnet · Time: 25 min

Repeat the Build 3 pattern for the remaining subagents on the diagram (the walkthrough example adds an outreach subagent and a QA subagent), then audit the full system for drift.

Steps:

In a new session with the Chief of Staff folder selected, feed the diagram as context for the next subagent's job, inputs, outputs, and report structure.

Have a clarifying back-and-forth on scope, tools, and handoff target before building anything — update the diagram to reflect what's clarified.

Create the agent identity file in .claude/agents/ via the build prompt: name, description with trigger phrases and reactive/proactive status, an explicit tools allowlist (real connector names only, no hardcoding), inferred static references (CRM, wiki file, database), a Job section mirroring the diagram's In/Returns steps, and a closing "must never do" line. Update routing in both CLAUDE.md and the new agent's own file.

Once all subagents exist, run the audit prompt to check the whole system against the diagram and CLAUDE.md — missing routing, overly broad tools, ungated irreversible actions, missing explicit handoff steps.

Run a full test prompt exercising the whole system and review the trace of subagent calls.

Reusable prompt — build a subagent from the diagram:

Goal: Create a subagent for [node name] directly from the refined diagram at diagrams/agent-system-diagram.html.

Context: That node's label and its In/Returns edges are the entire scope, nothing invented beyond what's on the diagram.

Rules:

- Ask any clarifying questions you need first (data store, reactive vs proactive, anything unclear)

- Look up the real live tool names for whatever connector this needs, don't hardcode

- Infer any static references (a CRM, a wiki file, an existing database) this job's input depends on and point the agent at them yourself

- Create .claude/agents/[node-name].md with: name matching the node, a description with trigger phrases and reactive/proactive status, tools as an explicit allowlist of only the real names needed, model sonnet, a reference section for anything inferred above, a Job section as an ordered checklist mirroring In steps Returns, and a closing line on what it must never do

- Test it against the diagram's In/Returns before calling it done

- Update routing: a line in CLAUDE.md naming this subagent and when to call it, and a line in the agent's own file naming the orchestrator and its siblings



Reusable prompt — audit the full subagent system:

Goal: Audit every subagent in .claude/agents against the system diagram and CLAUDE.md.

Context: Subagents get added over time and can drift, missing routing updates, tools broader than the job needs, gated actions that aren't actually gated, or a Job section that stops after its own task instead of handing off.

Rules:

- Read every file in .claude/agents and the current diagram at diagrams/agent-system-diagram.html

- For each subagent, confirm CLAUDE.md has a routing rule naming it and when to call it

- Confirm the subagent's own file names the orchestrator and its sibling subagents

- Confirm the Job section's last step actually hands back to the orchestrator, and preloads the next subagent to call per the diagram's Returns edge, not just "return the result" with no next step named

- Confirm its tools allowlist matches only what its diagram job needs, flag anything broader

- Confirm any action the diagram marks as human-gated (sending, publishing, anything irreversible) is NOT in that subagent's tools list

- Do not edit anything. Report findings only: which subagents are missing routing, which have excess tools, which are missing a gate they should have, which have no explicit handoff step to the next subagent



Go further: build a /review skill using parallel subagents; build a skill that keeps the diagram honest.
