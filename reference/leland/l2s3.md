Level 2, Session 3: Build Your Second Brain

Session summary

Scope a knowledge wiki, fill it with real articles from your own work, and set up the /ingest and /lint skills that keep it current. The goal is a living, cross-linked reference an agent can read on its own — instead of re-pasting client lists, project status, and team context into every new conversation.

/ingest and /lint skills set up to keep the wiki running without manual prompts

What makes a wiki AI-readable is specificity and linkage: a clients.md listing fifteen names is hard to navigate; a jen-martinez.md explaining her role and priorities and linking to [[q2-project]] is something an agent can act on.

Build 1 — Scope your knowledge wiki

Model: Sonnet · Time: 20 min

Agree on what the wiki is for before creating anything — the folder structure and operating contract shape every article added from here on.

Steps:

In the my-agents project, run the scoping-interview prompt — it pulls from CLAUDE.md, memory, prior conversation, and connected tools, drafts v1 answers with citations, and asks you to confirm/correct one question at a time across 5 areas (role, key people, top 3–5 projects, communication style, wiki scope).

Consider the four starter article types (People, Projects, Decisions, Preferences) as a starting structure.

Ask the agent to propose article types based on the interview, using the standard knowledge-wiki/ skeleton (CLAUDE.md, index.md, log.md, raw/, articles/[type]/).

Scaffold the folder structure, write the wiki's own CLAUDE.md operating contract, and initialize index.md with a section per article type — subfolders start empty (filled in Build 3).

Read the generated knowledge-wiki/CLAUDE.md and adjust anything that doesn't match the scoping conversation before building further.

Reusable prompt — scoping interview:

Goal: Interview me to gather the context you need to scope my knowledge wiki, don't create anything yet.

Context: Pull from anything you already have access to, my CLAUDE.md, memory files, prior conversation history, and connected tools (Slack, Notion, Linear, Databricks, Gmail, Granola, etc.). For each question, draft a v1 answer from what you found and cite where each piece came from, then ask me to confirm, correct, or add what's missing.

Cover these five areas:

1) My role and what I do day-to-day

2) The people I work with most, direct reports, peers, key stakeholders, clients (look them up in Slack to get real titles, not joke ones)

3) My current top 3-5 projects or priorities

4) How I communicate, tone, format preferences, banned words, what I avoid (check for a voice guide or banned-words list before asking)

5) What's in scope and out of scope for the wiki

Rules:

- One question at a time, wait for my reply before moving on

- Keep each question specific, no open-ended "anything else?" If I give a short answer, infer the rest from context before pushing back

- Don't ask me things you can already answer from CLAUDE.md or memory, confirm them instead

- If a tool lookup takes more than 2 attempts, stop and ask me directly

- After my last answer, summarize what you heard

- Don't create the wiki or write any files yet



Reusable prompt — propose article types:

Goal: Propose the article types my knowledge wiki should track, and what each one will contain.

Context: Base this on what I just told you in the scoping interview. My wiki will have the foundational documents below, then article types (subtypes within a type are fine if needed):

knowledge-wiki/

├── CLAUDE.md

├── index.md

├── log.md

├── raw/

└── articles/

├── [type-1]/

├── [type-2]/

└── [type-N]/

Rules:

- List the proposed structure of article types and what each will contain



Reusable prompt — scaffold the wiki + operating contract:

Goal: Scaffold my knowledge-wiki/ folder, write the operating contract in CLAUDE.md, and initialize index.md.

Context: Use the article types we landed on (e.g. people/, projects/, decisions/, preferences/), one subfolder per type, each holding one .md file per entity (e.g. articles/people/jen-martinez.md). Subfolders start empty; we'll fill them in Build 3.

Create this structure:

knowledge-wiki/

├── CLAUDE.md

├── index.md

├── log.md

├── raw/

└── articles/

├── [type-1]/

├── [type-2]/

└── [type-N]/

Rules:

- Write knowledge-wiki/CLAUDE.md including: what this wiki is for; the article types we landed on, each with one example; the folder convention (one subfolder per article type under articles/, one slugified .md file per entity, e.g. jen-martinez.md); a navigation rule (read index.md first to see what exists, then pull only the articles needed); a source citation rule (every article starts with a "Source: [where it came from]" line); and a Maintenance Protocol with two rules, Capture wide (drop anything into raw/ without filtering) and Lint often (scan periodically for stale facts, contradictions, and orphaned articles; flag before deleting)

- Populate index.md with a section heading for each article type (e.g. ## People, ## Projects)

- Use the exact article types from our conversation, not generic defaults

- Don't fill in any articles yet; leave log.md empty for now



Go further: add a Source Authority section; read the Karpathy LLM Wiki pattern.

Build 2 — Map what your AI needs to know

Model: Sonnet · Time: 15 min

Decide what belongs in the root CLAUDE.md (operating instructions) vs. the new wiki (stable domain knowledge), and migrate the first items.

Steps:

Open the project-root CLAUDE.md (in .claude, not the new knowledge-wiki/CLAUDE.md) and run the audit prompt.

Read the flagged items and pick 2–3 to move or add to the wiki.

Have the agent add each picked item to the appropriate wiki article type.

Reusable prompt — identify wiki candidates:

Goal: Identify anything in my CLAUDE.md that would work better as a wiki article than as operating instructions.

Context: Look at the CLAUDE.md in my .claude folder, not the one inside knowledge-wiki/. Use the four types of AI knowledge (in-context, wiki, connected tools, RAG) as your framework.

Rules:

- For each item flagged, explain why it belongs in the wiki

- Suggest which article type it belongs to



Go further: stockpile sources for Build 3.

Build 3 — Ingest data and view your wiki map

Model: Sonnet · Time: 25 min

Fill the wiki with real articles: give it sources, let the agent turn them into articles, review and refine, then visualize the result in Obsidian.

Steps:

Download Obsidian (obsidian.md) and point it at the knowledge-wiki folder for a visual, linked knowledge graph — plain .md files the agent also reads directly.

Add sources manually to knowledge-wiki/raw/ (resume/bio, recent meeting notes, an intro doc, anything with real information about role/people/projects) — no filtering needed, that's the point of raw/.

Or have the agent pull sources automatically from connected tools and the working directory into raw/ via the pull-sources prompt.

Have the agent read everything in raw/ and generate wiki articles per the CLAUDE.md article types, updating index.md and appending to log.md.

Review the generated articles in articles/[type]/ — edit one yourself, approve one as-is, ask the agent to revise one, to build the habit of staying in the editor seat.

Once satisfied, ask the agent to add [[wikilinks]] cross-referencing related articles (e.g., a People article linking to Project articles that mention that person).

Open the knowledge-wiki folder in Obsidian as a vault (File → Open Vault), then open Graph View — each article is a node, each [[wikilink]] an edge; isolated nodes need more cross-linking.

Reusable prompt — pull sources into raw/:

Goal: Pull raw source material from my connected tools and working directory into knowledge-wiki/raw/.

Context: Focus on recent meeting notes, project docs, team intros, role descriptions, planning docs, and anything that names the people I work with or the projects I own.

Rules:

- Save each source as a .md file in knowledge-wiki/raw/ with a slugified filename (a copy, or a clear summary with a link back to the original)

- Include a Source: line at the top of each file with where it came from and the date

- Don't filter or interpret yet, capture wide

- When done, list what you added



Reusable prompt — generate wiki articles from raw sources:

Goal: Read the files I just added to raw/ and create wiki articles from what's in them.

Context: Follow the article types defined in CLAUDE.md.

Rules:

- Each article goes in its type subfolder (e.g. articles/people/jen-martinez.md)

- Update knowledge-wiki/index.md with a one-line description of each new article under the right type heading

- Append an entry to knowledge-wiki/log.md with today's date and what you added



Go further: bulletproof articles with confidence scores; keep feeding the wiki.

Build 4 — Set up a system to scale and maintain your wiki

Model: Sonnet · Time: 20 min

Turn the manual ingest and review prompts into two reusable slash-command skills so the wiki keeps running without remembering the exact prompt each time.

Steps:

Create the /ingest skill (saved to .claude/skills/ingest/SKILL.md) — turns any new source (URL, file, pasted text) into structured wiki article updates.

Create the /lint skill (saved to .claude/skills/lint/SKILL.md) — performs a health check across all articles for orphaned files, stale facts, and contradictions, without auto-editing.

Test both: drop a second source into raw/, run /ingest, confirm index.md/log.md updated and new articles link to related ones.

Run /lint on the current wiki and approve any sensible prunes.

Reusable prompt — build /ingest skill:

Goal: Create an /ingest skill saved to .claude/skills/ingest/SKILL.md.

Context: Given any new source (URL, file, or pasted text), the skill turns it into structured wiki articles.

Rules:

- Extract only key facts, decisions, and insights, distill to what's durable and reusable, don't copy the full source

- At the top of any new article or updated section, include a Source line noting where the information came from

- Identify which existing articles the new information affects; update them, or create a new one if nothing related exists. New articles go in the right type subfolder (e.g. articles/people/jen-martinez.md)

- Keep each article focused and scannable, short paragraphs, bullets, no filler

- Add any new articles to knowledge-wiki/index.md under the right type heading with a one-line description

- Use [[wikilinks]] to link to any related article by filename

- Append an entry to knowledge-wiki/log.md with the date, source name, and a one-line note on what changed



Reusable prompt — build /lint skill:

Goal: Create a /lint skill saved to .claude/skills/lint/SKILL.md.

Context: The skill performs a health check on the knowledge wiki.

Rules:

- Scan all articles in articles/ for: orphaned files (nothing links to them), stale facts, and contradictions between articles

- Output a numbered list of suggested changes with a reason for each

- Don't delete or edit anything without my approval



Go further: make lint a habit; extend /lint; wire the wiki into the Session 2 email automation so every draft pulls live context.
