Build 1 — Write a rubric for your subagent

Model: Sonnet · Time: 20 min

Pick the subagent whose output matters most (customer-facing or expensive to get wrong) and write its rubric — a file the subagent itself never sees or references. Only the Build 3 evaluator reads it, and its dimension names become the Build 2 log's columns.

Steps:

Run the rubric-interview prompt — it reads the subagent's definition, asks 3 questions one at a time (what good output looks like, what an obvious failure looks like, what's gone wrong before or is most feared), then writes evals/rubrics/[subagent name].md with 3–5 checkable dimensions, rejecting any dimension that requires interpretation.

Manually review every dimension: for each, ask "could I point at a line in an output and say that's why this is a 1 and not a 3?" Rewrite or delete anything that fails this test — this step can't be delegated.

Run the deterministic-checks prompt to append a plain list of non-judged checks (things like right subagent, required sections present, length range, forbidden strings) to the bottom of the rubric file.

Reusable prompt — build the rubric via interview:

Do this for my [subagent name].

Read .claude/agents/[subagent name].md so you already know what this subagent does. Then conduct a structured interview with me before creating any files. Ask me these three questions one at a time and wait for my answers before moving on:

1. What does good output from the [subagent name] look like?

2. What would be an obvious failure for [subagent name] output?

3. What has this subagent gotten wrong before, in your own words? If it hasn't, what am I most afraid it will get wrong?

Once you have my answers, turn them into a rubric file at evals/rubrics/[subagent name].md with three to five dimensions. Every dimension must be checkable by reading the output. Reject any dimension I give you that requires interpretation, and tell me why, then propose a checkable version.

Do not modify .claude/agents/[subagent name].md. That subagent must never reference or be able to find this rubric.

Format:

# Rubric: [subagent name] Dimensions

Version: 1

| Dimension | What it measures | Score 1 | Score 3 | Score 5 |

|-----------|------------------|---------|---------|---------|

| [name] | [one sentence] | [bad] | [ok] | [good] |

Only three scores exist: 1, 3, and 5. Write all three for every dimension, each concrete enough that I could point at a line in an output and defend the score. Note at the top of the file that 2 and 4 are not valid scores.



Reusable prompt — add deterministic checks:

Do this for my [subagent name].

Read .claude/agents/[subagent name].md and evals/rubrics/[subagent name].md. Ask me what deterministic checks I want my evaluator to run on this subagent's output, in general, not per rubric dimension. If I don't know where to start, suggest a few options based on what this subagent's definition says it produces and what's gone wrong before, then let me pick, change, or add my own.

Once I've told you which checks I want, write them as a plain list at the bottom of evals/rubrics/[subagent name].md. Do not modify .claude/agents/[subagent name].md.



Go further: write the good and bad examples yourself; write a rubric for every other subagent.

Build 2 — Create the eval log and write the headers

Model: Sonnet · Time: 10 min

Create the log file with a header row derived directly from the rubric's dimension names — you write no headers by hand, but you do verify them.

Steps:

Run the log-creation prompt — it reads the rubric and writes evals/log/[subagent name].csv with a fixed column order (run_id, output_path, checks, one [dimension]_score column per rubric dimension, composite_score, suggested_edit, user_edit, action).

Open the CSV and confirm the dimension columns match the rubric spelling exactly, with nothing extra added.

Reusable prompt — create the eval log header:

Do this for my [subagent name].

Read evals/rubrics/[subagent name].md. Create evals/log/[subagent name].csv containing a single header row and no data rows, with these columns in this exact order:

run_id, output_path, checks, then one column per rubric dimension named [dimension_name]_score, then composite_score, suggested_edit, user_edit, action

Use lowercase snake_case for the dimension column names. Quote any field that could contain a comma so the file stays parseable when suggested_edit gets long. Do not add any columns I did not list, and tell me which dimension names you pulled from the rubric. Commit when done.



Alternate paths offered: Notion or Airtable instead of CSV.

Go further: add a routing log to grade the orchestrator; log files for the rest of the pipeline.

Build 3 — Send every output to an evaluator

Model: Sonnet · Time: 25 min

Build a dropbox hook that captures every finished output the moment it lands, and an evaluator subagent that scores everything sitting in that dropbox against the rubric.

Steps:

Add a SubagentStop hook to .claude/settings.json, scoped only to the target subagent — it skips short/question-mark/acknowledgment-style messages (mid-task check-ins, not deliverables) and otherwise writes a timestamped file to evals/inbox/[subagent name]/ containing the subagent name, timestamp, request summary, transcript path, and the full output.

Restart the session and send the subagent a real (not invented) request; confirm a file lands in the inbox folder afterward.

Build the evaluator subagent (.claude/agents/evaluator.md) — the only agent allowed to read rubrics — which: reads the rubric (and anchors file, if any), processes every inbox file oldest-first, runs all 5 deterministic checks regardless of early failures, makes a separate judge call per rubric dimension (score must be exactly 1, 3, or 5, quoting the justifying line or returning Unknown), computes a mean composite_score, writes suggested_edit lines for any failing check or sub-5 dimension (naming the exact fix location — skill/tool/context/routing), moves processed files from inbox/ to runs/ (never deletes), and never writes user_edit/action or edits a rubric/anchors/agent file itself.

Invoke the evaluator to empty the inbox.

Grade the grader on one row: open the worst-scoring row, read the output beside the suggested_edit evidence, and decide whether you'd have scored it the same.

Write your own fix into user_edit on that row by hand — sharper or narrower than the judge's, even if you agree with it.

Reusable prompt — add the dropbox hook:

Do this for my [subagent name].

Add a SubagentStop hook to .claude/settings.json that fires only for the [subagent name] subagent and for nothing else. Before writing anything, check last_assistant_message: skip the write entirely if it's short (under 40 words), ends in a question mark, or reads like an acknowledgment rather than finished work, since those are mid-task check-ins, not the deliverable. Otherwise, write one file to evals/inbox/[subagent name]/[YYYY-MM-DD]-[HHMMSS].md containing: the subagent name, the UTC timestamp, a one-line summary of the request, the transcript path from the transcript_path the hook receives, and then the subagent's full output, taken from the last_assistant_message field the hook receives and not by reading the transcript file.

The hook must not read any rubric, must not write to the log, and must not score anything. Show me the settings.json you wrote and explain what each part does before I restart.



Reusable prompt — build the evaluator subagent:

Do this for my [subagent name].

Create a new subagent at .claude/agents/evaluator.md. It grades finished outputs, never agents. It is also the only agent in my pipeline allowed to read rubrics. I invoke it with a subagent name, which it uses only to know which inbox to empty, which rubric to score against, and which log file to append to. When I invoke it that way, it should:

1. Read the rubric from evals/rubrics/[subagent-name].md including its REQUIRED SECTIONS, LENGTH RANGE, and FORBIDDEN STRINGS, and evals/anchors/[subagent-name].md if that file exists. If there are no anchors, run without them.

2. Process every file in evals/inbox/[subagent-name]/, oldest first.

3. For each file, append a row to evals/log/[subagent-name].csv with run_id set to the inbox filename minus its .md extension. Write output_path as the path the file will live at after step 9, not the inbox path it is at now, so the row still points at the output after the file moves. Quote every text field so a comma inside an edit can't break the row.

4. Run all five deterministic checks: right subagent, real output present, required sections, length range, forbidden strings. Run all five even if an earlier one fails. Write a single PASS to the checks column only if all five passed, otherwise FAIL.

5. For each rubric dimension, make a separate judge call that sees the rubric row for that dimension, any anchors, and the output. The score must be exactly 1, 3, or 5, matching one of the three written descriptions in the rubric. Never emit a 2 or a 4, and never emit a decimal. The judge must quote the line from the output that justifies its score before giving the score, and must return Unknown rather than guessing if the output doesn't contain enough to judge. Write the score to [dimension]_score.

6. Write composite_score as the mean of the dimension scores rounded to one decimal.

7. Do not label rows PASS or FAIL. There is no pass mark. Score every row and leave the judgment to me.

8. Whenever checks is FAIL or any dimension scored below 5, write to suggested_edit. Use one line per problem, in this format: the dimension name or failed check, then the quote from the output that proves it, then an arrow, then the specific change and the exact file path it belongs in. Decide that file by sorting the problem into skill, tool, context, or routing. Keep each line to one sentence after the arrow. Example: `source_traceability: "according to industry reports" → require a named source per claim in .claude/skills/research/SKILL.md`

9. Move each processed file from evals/inbox/ to evals/runs/[subagent-name]/ so it isn't scored twice. Never delete one, and never delete anything in evals/runs/.

10. Never write to user_edit or action.

11. Never edit a rubric, an anchors file, or anything in .claude/agents/.

12. Commit when the inbox is empty.



Reusable prompt — run the evaluator:

Do this for my [subagent name].

Invoke the evaluator subagent and have it process every file in evals/inbox/[subagent name]/.



Go further: only log rows that need attention; keep checking the judge as the rubric changes; extend to the rest of the pipeline.

Build 4 — Close the loop and put it on a schedule

Model: Sonnet · Time: 15 min

Set an approval policy for applying fixes, then split the loop: grading runs daily, applying fixes runs weekly — the gap between the two is the review window.

Steps:

Run the approval-policy prompt — it interviews you on Opt In (nothing applied unless you set action to Apply) vs. Opt Out (everything with a suggested edit applies at week's end unless set to Skip), asks which files should never be auto-edited, then creates a scheduled Friday 4pm task that applies rows per your policy (with user_edit always taking precedence over suggested_edit), sets action to Applied, commits, and sends a weekly summary (outputs graded, average composite vs. last week, files edited, rows still blank, a reminder to spot-check 5 rows).

If Opt In was chosen, manually mark action as Apply/Skip on individual rows rather than delegating that judgment call.

Schedule the grading side separately to run every weekday morning — it only invokes the evaluator and commits, never edits a skill/CLAUDE.md/user_edit/action, and only messages you if something needs attention (a FAIL, a dimension scored 1, or a growing blank-action count).

Reusable prompt — set approval policy + weekly apply schedule:

Do this for my [subagent name].

Interview me before writing anything. Ask me to pick A or B, and explain the tradeoff before I answer:

A) Opt in. Nothing is applied unless I set action to Apply myself. Safest, but if I skip a week nothing improves.

B) Opt out. Everything with a suggested edit is applied at the end of the week unless I set action to Skip. Faster, but a fix I never read still ships.

Then ask me which files should never be edited without my explicit approval, whatever I picked above.

Once I've answered both, create a scheduled task that runs every Friday at 4pm and encodes my answers. It applies rows in evals/log/[subagent name].csv: if I picked A, only rows where action is Apply. If I picked B, every row with a suggested_edit except where action is Skip. Either way, follow the user_edit precedence rule: if user_edit has content, use that and ignore suggested_edit entirely. Edit only the file each edit names, never a file I listed as protected, and never a rubric or an anchors file. Set action to Applied on each row it applies, then commit with a message listing the run IDs.

Then send me a summary with five things: how many outputs were graded this week, the average composite compared to last week, which files got edited, how many rows are still waiting with a blank action, and a reminder to read five rows and check whether I agree with the scores.

Write my two answers in plain language at the top of the task, so I can read my own policy without opening anything else.



Reusable prompt — schedule daily grading:

Do this for my [subagent name].

Create a scheduled task that runs every weekday at 7am. It should invoke the evaluator subagent to process every file in evals/inbox/[subagent name]/, then commit. It must not apply any fix, must not edit any skill file or CLAUDE.md, and must not write to user_edit or action. Then message me only if something needs my attention: any row where checks is FAIL, any row where a dimension scored a 1, and the count of rows now waiting with a blank action. If nothing qualifies, say nothing.



Go further: add a rollback guard; watch the buckets, not the scores.
